# 집알림 요구사항 재정의

- 작성일: 2026-08-19
- 상태: 승인됨 (0·1단계 구현 완료 2026-08-19)
- 대체하는 문서: `docs/ROADMAP.md`의 단계 순서 (이 문서가 우선한다)

## 1. 목표

**당첨될 때까지 계속 지원하면서, 매번 내 조건에 맞는 공고를 놓치지 않고 골라 지원한다.**

기존 문서의 목표는 "공고를 모아서 보여준다"였다. 실제 목표는 다르다. 화면을 보러 오는 서비스가 아니라, **알림을 받고 지원하는 시스템**이며, 한 번이 아니라 **당첨될 때까지 반복**한다.

이 차이가 요구사항 전체를 결정한다.

- 한 번 신청하는 도구라면 이번 공고만 잘 보여주면 된다.
- 계속 지원하는 도구라면 **내가 뭘 지원했고, 왜 떨어졌고, 다음엔 뭐가 유리한지**가 쌓여야 한다.
- 놓친 공고는 다음 기회까지 몇 달~1년을 기다린다. 그래서 **수집 완전성이 최우선**이다.

## 2. 확정된 결정

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 대상 지역 | **서울 전체** (경기·인천 제외) | 거주 가능 범위. 기능을 위해 지역을 넓히지 않는다 |
| 사용 범위 | **개인 도구 1인** | 멀티유저·인증·개인정보 처리방침 전부 불필요 |
| 실행 위치 | **로컬 맥** (배포하지 않음) | 지금은 배포를 범위에서 제외. 나중에 이전 가능하게 설계 |
| 스케줄 | **launchd → `curl /api/cron`** | dev에서 `scheduled()`가 자동 실행되지 않으므로 HTTP 경로로 트리거 |
| 저장소 | **로컬 D1** (Miniflare, `.wrangler/`) | 배포 없이 동작. `hosting.json`의 `d1`을 `"DB"`로만 바꾸면 된다 |
| 텔레그램 | **발송 전용** | 나가는 요청뿐이라 공개 URL이 필요 없다 |
| 알림 링크 | **공식 LH·SH 페이지** | 폰에서 `localhost`는 열리지 않는다. 최종 목적지도 공식 페이지다 |
| 신청 자동화 | **제출 직전까지** | 마지막 제출은 사람이 누른다. 아래 4절 참고 |
| 판정 기준 | **정확도보다 누락 방지(recall)** | 동시 대상 공고가 10건 미만이다. 애매하면 보내고 원문 확인을 붙인다 |

### 나중에 배포로 옮길 때

로직을 `app/lib/notify.ts`에 두고 두 경로에서 호출한다. 이 구조면 배포 시 `notify.ts`를 수정하지 않는다.

```
app/lib/notify.ts             ← 실제 로직 (수집 → 판정 → 발송 → 기록)
app/api/cron/route.ts         ← 지금: launchd가 curl
worker/index.ts scheduled()   ← 나중: 배포하면 같은 함수 호출
```

## 3. 대상 현실 (실측)

2026-08-19 기준 실제 측정값이다. 설계 전제이므로 기록한다.

### 마이홈 모집공고 API

전국 응답 **274건**(`totalCount` 274, 300행 요청으로 전량 커버).

| 범위 | 건수 | 비고 |
| --- | --- | --- |
| 서울특별시 | **5** | 전세임대 4 + 행복주택 1(강북구 오현로 208) |
| 수도권 전체 | 71 | 서울 5 / 경기 52 / 인천 14 |

관심 지역을 3구에서 서울 전체로 넓혀도 **1건만 늘어난다**(강북구 행복주택). 지도·조감도 대상을 확보하려면 경기·인천이 필요한데(수도권 71건 중 주소 있는 공고 47건), 거주 범위가 서울이므로 채택하지 않는다.

### 지도·조감도 가능 여부

| 유형 | 서울 건수 | 지도 핀 | 조감도 |
| --- | --- | --- | --- |
| 전세임대 | 4 | ❌ 원리적 불가 (선정자가 직접 물색) | ❌ |
| 행복주택 | 1 | ✅ 구체 주소 있음 | ✅ 신축 |
| SH 매입임대·공공임대 | 1~5 | 일부 (첨부 주택목록) | ❌ 기존 건물 |

**전세임대가 서울 공고에서 가장 큰 비중을 차지하며, 전세임대에는 단지·주소·조감도가 존재하지 않는다.** 마이홈 서울 5건 중 4건이 전세임대이고, SH를 합한 동시 대상은 6~10건 규모다. 따라서 지도·조감도 요구사항은 최하위이며 주소가 있는 공고에만 동작한다.

### SH 수집 결함 (0단계의 근거) — 2026-08-19 해소

원인은 **세 가지**였고, 처음 의심했던 `srchWord="모집"`은 원인이 아니었다.
`srchWord`는 서버가 제목으로 걸러주는 것이라 오히려 같은 페이지 수로 더 많은
모집공고를 가져온다. 유지하는 것이 맞다.

| 원인 | 영향 |
| --- | --- |
| **3구 필터** (`서초·강남·송파`) | 금천·양천·강동·성북 등 다른 서울 자치구를 언급한 공고를 전량 폐기 |
| **1페이지 제한** | 게시판 10행만 읽어 접수 중인 과거 공고를 놓침 |
| **`followUpWords` 누락** | `입주대상자 발표`가 없어 끝난 공고의 결과 발표를 모집공고로 채택 |

`srchWord="모집"` 유지 시 페이지별 누적 모집공고: 1p→6, 2p→13, 3p→16, 4p→21, **5p→31**.
따라서 `SH_LIST_PAGE_COUNT = 5`로 정했다.

**수정 후 실측**: 전체 수집 **5건 → 36건** (LH 5 + SH 31). 후속공고 오탐 0,
중복 0, 비서울 자치구 0. 강북구 행복주택(주소가 있는 유일한 서울 공고)도
3구 필터에서 버려지던 것이 이제 수집된다.

자치구를 25개로 넓히면서 드러난 결함도 함께 고쳤다. `shortDistrictName`이
`replace("구","")`였기 때문에 `중구`가 `중`이 되어 "모집 중" 같은 제목이 모두
중구로 분류되고, `구로구`는 앞의 `구`가 지워져 `로구`가 되어 "구로"로 시작하는
제목을 놓쳤다. 끝의 `구`만 떼고 한 글자로 줄어들면 약칭을 쓰지 않도록 바꿨다.

### 파싱 CPU 비용

로컬 실행에서는 제약이 아니지만, 나중에 Cloudflare 무료 플랜(Cron Trigger당 CPU 10ms)으로 옮길 때 판단 근거가 되므로 기록한다.

| 작업 | 페이로드 | CPU |
| --- | --- | --- |
| 목록 수집 전체 | 364KB JSON + 126KB HTML | 1.94 ms |
| 상세 파싱 1건 | 100KB | 2.44 ms |
| 상세 파싱 1건 | 300KB | 6.89 ms |
| 상세 파싱 1건 | 600KB | 10.50 ms |

목록 기반 알림은 무료 한도의 19%로 여유가 있다. 상세 요약까지 담으면 1건에 한도의 70%를 쓴다. 그때는 `stripHtmlToText`의 13단계 순차 `.replace()`를 3패스로 통합하면 약 1/4로 줄어든다(동작 보존 검증이 선행 조건).

## 4. 신청 자동화의 한계선

**제출 직전까지 자동화하고, 최종 제출은 사람이 누른다.**

이유는 두 가지다.

1. LH 청약센터·SH 인터넷청약은 공동인증서·간편인증 본인인증이 필수다. 자동 제출하려면 인증수단을 대리 보유해야 한다.
2. 청약 신청은 법적 신고행위다. 착오·허위 신청 시 당첨 취소·부적격 처리·일정기간 청약 제한이 신청자 본인에게 돌아간다.

자동화하는 범위는 다음까지다.

- 조건 판정 → 알림 → 신청서에 넣을 값 정리 → 필요 서류 체크리스트 → 마감 D-1 알림 → 공식 신청 페이지 해당 위치로 원클릭 이동

## 5. 요구사항

우선순위는 원래 구두로 말한 순서와 다르다. 변경 근거를 함께 적는다.

| 우선 | ID | 요구사항 | 근거 |
| --- | --- | --- | --- |
| 1 | **R0** | **수집 완전성** — 서울 공고 누락 0, 오탐 0 | 실측으로 SH 4건 누락 확인. 놓치면 다음 기회까지 수개월. 나머지 전부의 전제 |
| 2 | **R1** | **텔레그램 알림** | 핵심 가치. 동시 대상이 10건 미만이라 스팸 위험이 없다 |
| 3 | **R2** | **지원 준비 + 지원 이력 기록** | "계속 지원"의 핵심. 기록이 없으면 매번 같은 판단을 처음부터 다시 한다 |
| 4 | **R3** | **자격 창(window) 추적** | 조건은 그대로인데 시간이 지나면 자격이 닫힌다. 계속 지원하는 사람에게 가장 실질적 |
| 5 | **R4** | **전세임대 전용 정보** | 서울 공고의 최대 비중(마이홈 서울 5건 중 4건). 지원한도액·본인부담·물색조건·계약절차 |
| 6 | **R5** | **조건 판정 고도화** | 동시 대상이 10건 미만이라 정교한 엔진이 불필요. 누락 방지가 우선 |
| 7 | **R6** | **경쟁률 이력 → 현실성 판단** | 계속 지원하려면 어디에 힘을 쓸지 골라야 한다 |
| 8 | **R7** | **위치 + 주변 지하철역** | 주소 있는 공고에만 동작. 서울 대상 소수 |
| 9 | **R8** | **조감도·외관** | 전세임대·매입임대에는 존재하지 않는다. 신축이 뜰 때만 |

### 원래 순서와 달라진 점

- **R0가 신규로 최상위**에 올라왔다. 수집이 안 되면 판정도 알림도 의미가 없다.
- **조건 판정이 1순위에서 6순위로 내려갔다.** 동시 대상이 10건 미만이라 정확도보다 누락 방지가 중요하다.
- **R2(지원 이력)와 R3(자격 창)이 신규 추가**되었다. "계속 지원한다"는 요구에서 파생된다.
- **R4(전세임대 정보)가 신규 추가**되었다. 서울 공고의 실제 다수를 차지하는데 현재 가장 다루지 못하는 유형이다.
- 조감도·지하철역은 최하위로 내려갔다. 대상 공고가 사실상 없다.

### R3 자격 창 상세

| 유형 | 기준 | 31세 미혼 1인가구 기준 |
| --- | --- | --- |
| 청년 | 만 39세 이하 | 약 8년 남음 |
| 신혼부부 | 혼인 7년 이내 | 미해당 (혼인 시 열림) |
| 다자녀·신생아 | 자녀 수·연령 | 미해당 |
| 고령자 | 연령 하한 | 아직 멀다 |
| 누적형 | 청약통장 가입기간·무주택기간·거주기간 | 시간이 지나면 유리해짐 |

"곧 자격이 닫히는 유형"을 경고하는 것이 이 요구사항의 핵심 산출물이다.

## 6. 웹사이트의 역할

알림이 생기면 웹사이트의 성격이 바뀐다. "내가 찾아보는 곳"에서 "알림 받고 행동하는 곳"이 된다.

| | 텔레그램 | 웹사이트 |
| --- | --- | --- |
| 역할 | **트리거** — 놓치지 않게 | **판단과 준비** — 정확하게 |
| 담는 것 | 공고명·마감·판정 한 줄·공식 링크 | 신청자격 전문·서류·이력·지도 |
| 상태 | 없음 | 있음 (프로필·체크리스트·이력) |

텔레그램만으로는 부족하다. 숫자 6개·토글 5개짜리 프로필 입력을 채팅으로 하는 것은 비효율이고, 서류 체크리스트와 지원 이력은 상태가 필요하다.

| ID | 요구사항 | 현재 상태 |
| --- | --- | --- |
| **W1** | **프로필 저장** — 한 번 입력하면 유지. cron이 이 값으로 판정 | ❌ 브라우저 메모리뿐. 새로고침하면 기본값으로 리셋 |
| **W2** | **지원 이력 화면** — 무엇을 언제 어떤 순위로 지원했고 결과가 무엇인가 | ❌ 없음 |
| **W3** | **지원 준비 화면** — 내 값 정리·서류 체크리스트·마감 D-day·원클릭 이동 | ❌ 공식 링크만 있음 |
| **W4** | **자격 창 표시** — 곧 닫히는 유형 경고 | ❌ 없음 |
| **W5** | **알림 설정** — 유형·발송 시각 | ❌ 없음 |
| **W6** | **판정 근거** — 왜 알림이 왔는지 / 왜 안 왔는지 | 부분 (판정 칩 존재) |
| **W7** | 전세임대 정보·지도·지하철·조감도 | ❌ (R4·R7·R8) |

**W1이 R1(알림)의 선행 조건이다.** cron이 브라우저 없이 판정하려면 프로필이 저장소에 있어야 한다. 이것이 기존 보안 경계("사용자 프로필은 브라우저 메모리에만 둔다")를 바꾸는 지점이며, 개인 도구이고 로컬 실행이므로 허용한다.

### 기존 화면에서 바뀌는 것

- `초기화` 버튼: 기본값 리셋 → **저장된 내 조건**으로 되돌리기
- `텔레그램 알림 미리보기`(현재 가짜): → **실제 발송 이력·상태**
- 프로필 사이드바: 상시 노출 → 한 번 저장하면 자주 볼 필요가 없으므로 설정으로 접기
- 공고 목록: 탐색 중심 → 알림에서 넘어온 한 건에 집중하는 화면 우선

## 7. 데이터 모델 (최소)

개인 도구이므로 프로필은 1행이다.

| 테이블 | 행 수 | 용도 |
| --- | --- | --- |
| `profile` | **1** | 나이·소득·자산·혼인·자녀·토글. cron이 읽고 웹에서 수정 |
| `sent_notice` | 공고당 1 | 알림 중복 발송 방지 (`notice_id`, `sent_at`) |
| `applied` | 지원당 1 | 공고·지원일·순위·결과·탈락사유 |

`sent_notice`(알림 보낸 기록)와 `applied`(내가 지원한 기록)는 다른 개념이며 둘 다 필요하다.

배선은 이미 존재한다. `.openai/hosting.json`의 `d1`을 `"DB"`로 바꾸면 `vite.config.ts`가 바인딩을 조립하고, `db/index.ts`의 `getDb()`가 동작한다. `drizzle.config.ts`가 이미 `db/schema.ts`를 가리키므로 `npm run db:generate`가 바로 돈다. 예시는 `examples/d1/`에 있다.

| 단계 | 내용 | 완료 조건 |
| --- | --- | --- |
| **0** ✅ | 수집 완전성 (R0) | SH 다중 페이지 수집 + `followUpWords` 교정. **검증 방법**: SH 게시판 1~3페이지를 사람이 눈으로 읽은 모집공고 목록과 수집 결과가 일치. 누락 0, 후속공고 오탐 0. 두 경우를 고정하는 회귀 테스트 추가 |
| **1** ✅ | D1 + 프로필 저장 (W1) + `applied` 테이블 | 프로필을 저장하고 새로고침 후에도 유지. 스키마 3개 생성. **서버 재시작 후에도 유지 확인** |
| **2** | 알림 파이프라인 (R1) | `notify.ts` + `/api/cron` + launchd + 텔레그램 봇. 하루 2~3회 실행 기준 **새 공고를 12시간 내 수신**, 같은 공고 재발송 0, 링크는 공식 페이지 |
| **3** | 지원 준비 + 이력 기록 (R2 · W2 · W3) | 서류 체크리스트·마감 D-day·원클릭 이동, 그리고 같은 흐름 안에서 "지원했음" 기록 |
| **4** | 자격 창 추적 (R3 · W4) | 청년 D-day 등 곧 닫히는 유형 경고 |
| **5** | 전세임대 전용 정보 (R4 · W7 일부) | 지원한도액·본인부담·물색조건 추출 |
| **6** | 판정 고도화 (R5) · 알림 설정 (W5) · 판정 근거 (W6) | |
| **7** | 경쟁률 이력 (R6) → 위치·지하철 (R7) → 조감도 (R8) · W7 잔여 | 주소 있는 공고에만 동작 |

3단계에서 "지원 준비"와 "이력 기록"을 같은 흐름에 두는 것이 중요하다. 신청 후 따로 기록하러 돌아오는 구조면 기록되지 않는다.

이 문서는 8개 단계를 담은 요구사항 정의다. **구현 계획은 단계별로 따로 작성한다.** 다음 산출물은 0단계(수집 완전성)의 구현 계획이며, 1단계 이후는 각 단계 착수 시점에 작성한다.

## 9. 하지 않는 것

기존 6개 금지사항을 유지하고 이 문서에서 확정된 항목을 더한다.

1. 상세 추출 API에 `apply.lh.or.kr`, `i-sh.co.kr`, `www.i-sh.co.kr` 외의 URL을 허용하지 않는다.
2. 전세임대 공고에 실제 공급주택이 있는 것처럼 **가상 좌표·핀·조감도를 만들지 않는다.** 주소도 단지 식별자도 없으면 구 단위 영역으로 표시한다.
3. 신청건수를 공식 최종 경쟁률로 표현하지 않는다. `경쟁률 숫자 : 1`이 공식 페이지에 있을 때만 표시하고, 없으면 `아직 집계 전`이다.
4. 공고 제목만으로 신청 가능을 확정하지 않는다.
5. **사용자 확인 없이 청약을 자동 제출하지 않으며, 인증수단을 대리 보유하지 않는다.**
6. 인증키를 브라우저 응답·HTML·오류 메시지에 노출하지 않는다.
7. **경기·인천 공고는 수집하지 않는다** (거주 범위 결정에 따름).
8. **배포하지 않는다** (현재 범위). 배포로 옮길 때 `notify.ts`를 재작성하지 않도록 분리는 유지한다.

## 10. 알려진 제약

로컬 실행을 선택한 결과로 받아들이는 제약이다.

| 제약 | 영향 | 대응 |
| --- | --- | --- |
| 맥이 잠들면 스케줄 시각에 실행되지 않는다 | 마감 임박 알림 지연 | launchd는 깨어난 직후 밀린 작업을 한 번 실행한다. 하루 2~3회면 실질적으로 충분. 더 엄격히 하려면 `pmset` 예약 wake |

## 12. 별도 처리 필요 (이 문서 범위 외)

2026-08-19 코드 정리 중 발견된 신뢰 경계 문제 두 건이다. 요구사항 변경과 무관하게 수정이 필요하다.

1. **수집 단계에서 상위 API URL이 검증 없이 링크로 렌더된다.** `notice-sources.ts`가 마이홈 응답의 `item.url`을 그대로 `sourceUrl`에 넣고, `page.tsx` 3곳이 `target="_blank"`로 렌더한다. 도메인 allowlist는 상세 읽기에만 적용되고 수집 단계에는 없다. 테스트도 `https://example.com/1`을 통과시킨다.
2. **상세 조회 실패가 `아직 집계 전`으로 표시된다.** 경쟁률 칸이 `noticeDetail?.competition.ratio ?? …` 형태여서, 추출 실패와 "공고에 경쟁률이 없음"이 같은 문구가 된다. 데이터 신뢰성이 핵심인 서비스에서 추출 실패를 공식 페이지에 대한 단정으로 표시하는 셈이다.
