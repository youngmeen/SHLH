# 집알림 ROADMAP

## 1. 목적

집알림의 구현 순서를 정의한다.

기능을 많이 만드는 것보다 `PRODUCT.md`의 **핵심 흐름**을 처음부터 끝까지 완성하는 것을 우선한다.

`PRODUCT.md`, `REQUIREMENTS.md`, `DOMAIN.md`에서 정의한 내용을 기준으로 구현한다.

---

## 2. 현재 상태

## Phase 0. 공고 수집 안정화

**상태: 완료**

구현 내용:

- 마이홈(국토교통부) 모집공고 API 수집 — LH 공고가 이 경로로 들어온다
- SH 모집공고 수집
- SH 다중 페이지 처리 (5페이지)
- 서울 전체 자치구 처리
- 모집공고와 후속공고 구분
- 중복 공고 제거
- 기존 3구 지역 필터 제거
- 자치구 약칭 판별 오류 수정 (`중구`·`구로구`)

현재 서울 공고를 수집할 수 있는 기본 구조가 마련된 상태다.

### 이 단계에 포함되지 않은 것

완료 범위를 정확히 남긴다. 아래는 Phase 0에서 하지 않았고, 이후 단계에서 다룬다.

- LH 독립 출처 수집 — 마이홈 API에 없는 LH 공고는 들어오지 않는다
- 수집한 공고의 저장 — 현재는 요청할 때마다 수집하고 저장하지 않는다
- 신규 공고 식별 (R3) — 처음 확인한 시점을 기록하지 않으므로 판단 근거가 없다
- 후속공고 보관 (R3) — 현재는 목록에서 제외하는 것이 아니라 폐기한다
- 정정 공고 구분 — 후속공고 판별 목록에 `정정`이 없다
- 제목에 `모집`이 없는 공고 — 현재 수집 조건에서 제외된다. R3의 "애매한 공고는 유지" 원칙과 어긋난다 (`SPEC.md` G5)

## Phase 1. 사용자 프로필 및 저장소

**상태: 완료 (범위 제한)**

구현 내용:

- 로컬 D1 사용 (Phase 2에서 Supabase Postgres로 이동한다 — `SPEC.md` S1)
- 사용자 프로필 저장 (`profile` 테이블 1행)
- 새로고침 및 서버 재시작 후 데이터 유지
- 지원 이력 테이블 `applied` 생성
- 알림 발송 기록 테이블 `sent_notice` 생성

브라우저가 실행되지 않은 상태에서도 서버가 사용자 프로필을 읽을 수 있다.

### 현재 저장하는 값

```text
현재 거주 자치구 목록 / 나이 / 세대원 수 / 월 소득 / 총자산
주택 보유 여부 / 혼인 상태 / 혼인일 / 자녀 수
막내 자녀 생년월일 / 임신 여부 / 한부모 여부
```

### R6 대비 부족한 값

Phase 3 착수 전에 채워야 한다.

- 생년월일 — 현재는 나이를 숫자로 저장한다. 생일이 지나면 틀린 값이 되고 자격 만료 시점(Phase 10)을 계산할 수 없다
- 현재 지역 거주 시작일
- 세대주 여부
- 세대구성원 무주택 여부 / 무주택 기간
- 본인 소득과 세대 소득 구분
- 자동차 가액
- 청약통장 (보유 여부·가입일·납입 횟수·납입 금액)

## 3. 앞으로의 구현 순서

## Phase 2. 공급주택 구조화와 저장

핵심 데이터 단위를 `Notice`에서 `HousingUnit`까지 확장하고, 수집 결과를 저장한다.

방법은 2026-08-20 스파이크로 확정됐다(`SPEC.md` 5절).

- 전용면적·주택 정보는 **단지정보 API**로 얻는다. 첨부 PDF는 다루지 않는다 (S3)
- 저장소를 **Supabase Postgres**로, 런타임을 **Node + Next.js**로 옮긴다 (S1)
- 저장 스키마 4테이블과 동기화 주기(하루 2회), 내보내기(백업)를 확정했다 (S2·S4·S6)

주요 대상 — 런타임·저장소 이동 · 마이홈 주택 단위 행 살리기 · 단지정보 API 결합 · 서울주거포털로 SH 접수기간 채우기 · 정정공고 연결 · 후속공고 보관(Phase 6 선행) · 공고·주택·이력 저장 · `[수집]` 버튼과 스케줄 · 내보내기.

저장을 이 단계에 넣는 이유는 신규 공고 식별(R3)에 최초 확인 시각이 필요하고, 파싱 규칙을 고쳤을 때 비교할 대상이 있어야 하기 때문이다.

전세임대는 HousingUnit이 없을 수 있으므로 구분까지만 하고 전용 분석은 Phase 5에서 한다.

**세부 계획·검증·완료 조건은 `CURRENT.md`에 있다.**

## Phase 3. 지원 자격 판정

### 목표

저장된 사용자 프로필과 공고 조건을 비교하여 **내가 해당 공고에 지원할 수 있는지 빠르게 판단한다.**

### 선행 조건

- 프로필을 생년월일 기반으로 전환한다 (Phase 1의 부족한 값 참고)
- 판정 기준일을 공고일로 고정한다 (R12)
- 공고에서 공급유형·순위(SupplyCategory)를 추출한다. 자격은 공고 단위가 아니라 순위 단위로 다르다

### 구현 대상

우선 실제 공고에서 자주 사용하는 조건부터 적용한다.

- 나이
- 무주택 조건
- 혼인 여부
- 소득
- 자산
- 자동차 가액
- 거주 조건
- 세대 조건
- 청약통장 조건
- 복지자격 (수급자·차상위·보호대상 한부모 등 순위 판정에 쓰이는 자격)
- 가구원수별 소득·자산 기준표 구조화

기존 제목 기반 판정(`app/lib/audience-match.ts`)은 AudienceType 추출로 정리하고, 그 위에 Eligibility를 새로 만든다. 같은 기능을 두 곳에 두지 않는다.

판정 상태와 원칙은 R12~R14를 따른다. 판정 결과와 근거를 함께 저장한다.

### 완료 조건

공고 하나를 열었을 때 다음과 같이 확인할 수 있어야 한다.

```text
청년 2순위 · 지원 가능

연령        충족
무주택      충족
소득        충족
자산        확인 필요
청약통장    확인 필요
```

## Phase 4. 생활권 및 주택 선호 판단

### 목표

지원 가능한 주택 중 **실제로 내가 살고 싶은 주택을 골라낸다.**

### 구현 대상

#### LivingBase

- 현재 주요 생활 거점 설정
- 생활 거점 주소 변경
- 회사 이전 및 이직 대응
- 이동수단 설정
- 허용 출퇴근 시간 설정

초기값:

```text
이동수단: 대중교통
허용 출퇴근 시간: 편도 50분
기준: Door-to-Door
```

#### 출퇴근 계산

- 주소 → 좌표 지오코딩 수단 선택
- 대중교통 경로·소요시간 외부 API 선택
- 계산 결과 캐시
- 주소를 확보하지 못한 주택 처리 (근사값은 추론 정보로 표시, 없으면 `확인 필요`)

주소는 Phase 2에서 단지정보 API로 확보한다(`SPEC.md` 5절). 주소를 얻지 못한 주택의 처리는 R10을 따른다.

#### 수집 범위 확장 — 경기도

경기도 판단을 하려면 경기도 공고가 들어와야 하므로 수집 확장을 이 단계에서 함께 한다.

**참고할 실측(2026-08-20)** — 마이홈 API의 수도권 행은 서울 5 · 경기 42 · 인천 14다. 서울 5건 중 4건은 전세임대라 주택 정보가 없다. 즉 Phase 2·3에서 검증할 주택 단위 데이터가 서울에는 사실상 행복주택 1건뿐이다. 경기 확장을 이 단계까지 미룰지, Phase 2로 끌어올릴지는 다시 판단할 여지가 있다.

- 마이홈 API의 서울 필터 해제 (경기 포함, 인천 제외)
- 지역 모델을 `시도 + 시군구`로 일반화 — 현재 타입은 서울 25개 자치구로 고정되어 있다
- 프로필의 거주지역·선호지역도 같은 모델로 전환
- 경기 지역 공급기관 출처 추가 검토 (SH는 서울 전용 게시판이다)

#### HousingPreference

R19의 조건 중 지역·전용면적·보증금·월 임대료·주택 유형·출퇴근 시간부터 적용한다.

결과는 `관심 높음 / 검토 / 관심 낮음` 3단계로만 낸다. 처음부터 추천 점수를 만들지 않는다. 서울·경기 판단 기준은 R11을 따른다.

### 완료 조건

하나의 공고에 공급주택이 여러 개 있을 경우 다음처럼 정리할 수 있어야 한다.

```text
총 20개

관심 높음 3
검토 6
관심 낮음 11
```

## Phase 5. 전세임대 전용 분석

### 목표

전세임대 공고에서 **실제로 판단에 필요한 정보를 정리한다.**

전세임대는 공고 시점에 공급주택이 존재하지 않으므로 Phase 2~4의 공급주택 중심 흐름이 적용되지 않는다. 이 단계 없이는 전세임대 공고가 분석되지 않은 상태로 남는다.

**확인됨(2026-08-20)** — 마이홈 API의 서울 공고 5건 중 **4건이 전세임대**이고 모두 `houseSn=0`으로 주택 정보가 없다(`SPEC.md` 5절). 즉 서울에서 LH 경로로 오는 공고는 대부분 이 단계 없이는 분석되지 않는다.

### 구현 대상

- 지원한도
- 본인 부담
- 물색 가능 지역
- 대상 주택 조건
- 임대 조건
- 계약 절차
- 주요 제한사항

### 원칙

- 존재하지 않는 주택이나 주소를 생성하지 않는다.
- 물색 가능 지역은 주택이 아니라 지역 범위로 다룬다.
- 출퇴근 판단은 개별 주택이 아니라 물색 가능 지역 단위로 적용한다.

### 완료 조건

전세임대 공고를 열었을 때 지원 가능 여부와 함께 지원한도·본인부담·물색 가능 지역을 확인할 수 있어야 한다.

## Phase 6. 과거 경쟁률 및 모집 이력

### 목표

현재 후보 주택이 과거에 어느 정도 경쟁이 있었는지 확인하여 **지원 우선순위 판단에 활용한다.**

### 선행 조건

Phase 2에서 보관한 후속공고(결과 발표·접수결과)가 경쟁률의 출처다. 후속공고를 폐기하고 있으면 이 단계를 시작할 수 없다.

비교 우선순위는 R24를 따른다. 다만 매입임대는 매번 다른 주택이 공급되므로 `동일 주택` 매칭이 성립하지 않는 경우가 많다. 지역·유형 단위 비교가 기본이 될 것을 전제로 만든다.

### 구현 대상

- 후속공고 수집과 파싱
- 후속공고와 원래 모집공고 연결
- 과거 모집공고·공급주택·공급형·순위별 경쟁률 저장
- 모집 세대수 / 신청자 수 / 공식 경쟁률 구분
- 경쟁률 추이 표시

원칙은 R26·R27을 따른다. 특히 정보 없음과 조회 실패를 구분한다(R43, `SPEC.md` G2).

### 완료 조건

관심 주택에서 가능한 경우 최근 과거 경쟁률을 함께 확인할 수 있어야 한다.

## Phase 7. 추천 및 우선순위

### 목표

앞선 분석 결과를 종합하여 **내가 무엇부터 확인해야 하는지 정리한다.**

### 초기 방식

지원 자격·주택 선호·출퇴근·임대조건·과거 경쟁률을 종합한다. 종합 순서는 `DOMAIN.md`의 Recommendation을 따른다.

복잡한 AI 추천이나 정밀 점수 모델을 사용하지 않는다. 명확한 규칙으로 `최우선 확인 / 추천 / 검토 / 관심 낮음` 4단계를 낸다.

### 예

```text
1. 성남 A주택 / 36㎡
   지원 가능
   출퇴근 37분
   보증금 적정
   과거 경쟁률 5.8:1
   → 최우선 확인

2. 송파 B주택 / 29㎡
   지원 가능
   출퇴근 31분
   면적 작음
   과거 경쟁률 21.4:1
   → 검토
```

### 완료 조건

공고 전체를 직접 읽지 않고도 우선 확인할 공급주택을 몇 개로 줄일 수 있어야 한다.

---

## Phase 8. 알림 발송

### 목표

새로운 공고가 발생했을 때 사용자가 사이트를 직접 확인하지 않아도 알 수 있도록 한다.

수집과 저장, 동기화 스케줄은 Phase 2에서 만든다. 이 단계는 **저장된 결과를 발송하는 것**이다.

분석 결과가 완성된 뒤에 알림을 만든다. 알림은 분석 결과를 전달하는 수단이며 분석 자체가 제품의 핵심이다(4절 결정 기록 참고).

### 구현 대상

- 알림 실행 로직 (실행 경로와 분리해 배포 시 재작성하지 않도록 둔다)
- 신규 공고 확인 (Phase 2에서 기록한 최초 확인 시점 사용)
- 사용자 프로필 기반 판정
- 관심 주택 요약
- 텔레그램 발송
- 발송 이력 저장 (`sent_notice`)
- 중복 발송 방지
- 공식 원문 링크 제공

### 알림 예시

```text
[신규 임대주택 공고]

SH 청년 매입임대

지원 가능
공급주택 24개
관심 후보 4개

1. 성남 A주택 / 36㎡
2. 송파 B주택 / 36㎡
3. 강남 C주택 / 29㎡

마감 D-6

[공식 공고 확인]
```

### 완료 조건

- 신규 관심 공고를 정상적인 스케줄 실행 기준 12시간 이내 확인
- 동일 공고 중복 발송 없음
- 공식 링크 사용
- 성공한 발송만 발송 이력에 기록

---

## Phase 9. 지원 준비 및 지원 이력

### 목표

관심 공고를 발견한 이후 실제 지원까지의 과정을 관리한다.

### 구현 대상

- 지원 준비 화면 (R33) — 신청 일정, 마감 D-day, 필요 서류, 확인할 조건, 지원 대상 주택
- 지원 기록 (R35)
- 지원 결과와 상세 사유 (R36·R37)

### 원칙

지원 준비와 지원 기록을 같은 흐름 안에서 처리한다.

신청 후 별도 화면으로 이동하여 기록하도록 강제하지 않는다.

### 완료 조건

관심 주택 확인부터 실제 지원 기록까지 하나의 흐름으로 처리할 수 있어야 한다.

---

## Phase 10. 자격 변화 추적

### 목표

시간이 지나면서 열리거나 닫히는 지원 자격을 추적한다.

### 주요 대상

- 청년 연령 제한
- 무주택 기간
- 거주 기간
- 청약통장 가입 기간
- 청약통장 납입 횟수
- 혼인 후 신혼부부 자격
- 자녀 관련 자격

### 핵심 기능

곧 사용할 수 없게 되는 자격을 우선적으로 알려준다.

예:

```text
청년 공급 자격
만 39세까지

남은 기간 약 2년 4개월
```

이 단계는 프로필이 생년월일·거주 시작일·청약통장 가입일을 저장하고 있어야 성립한다(Phase 3 선행 조건과 동일).

---

## Phase 11. 부가 정보 고도화

핵심 지원 흐름이 완성된 후 진행한다.

### 위치

- 지도
- 주변 지하철역
- 주요 생활시설

### 주택 정보

- 준공연도
- 건물 외관
- 조감도
- 주택 유형 상세

### 추천 고도화

- 과거 지원 결과
- 과거 경쟁률
- 지역별 경쟁 수준
- 사용자 선택 패턴

을 이용하여 추천 결과를 개선한다.

## 4. 결정 기록

단계 순서에 대해 명시적으로 정한 내용이다. 나중에 다시 논의하지 않기 위해 근거를 함께 남긴다.

| 결정 | 내용 | 근거 |
| --- | --- | --- |
| 알림 시점 | 분석이 완성된 **Phase 8**에 만든다 | 알림은 분석 결과를 전달하는 수단이다. 얇은 알림을 먼저 붙이면 내용이 계속 바뀌고 두 번 만들게 된다 |
| 감수하는 위험 | Phase 8 이전에는 새 공고를 사용자가 직접 확인해야 한다 | 공고를 놓치면 다음 기회까지 수개월이 걸린다. Phase 2에서 공고를 저장해 **최초 확인 시점 기록은 먼저 남기고**, 개발 기간에는 사이트를 직접 열어 확인한다 |
| 경기도 확장 | **Phase 4**에서 생활권 판단과 함께 한다 | 판단 기준 없이 경기 공고만 늘리면 목록이 지저분해진다. 수집 확장과 출퇴근 판단을 같은 단계에 둔다 |
| 전세임대 | **Phase 5**로 독립시킨다 | 공급주택이 존재하지 않아 Phase 2~4 흐름이 적용되지 않는다. 서울 LH 공고 5건 중 4건이 전세임대로 확인됐다 (`SPEC.md` 5절) |
| 순위 단위 판정 | 자격과 경쟁률을 SupplyCategory에 붙인다 | 같은 공고에서도 순위별로 자격 기준과 경쟁률이 다르다. Notice 단위로 만들면 Phase 6에서 다시 짜야 한다 |
| 저장소 | **Supabase Postgres (Free)** | 배포를 전제하면 저장소를 두 번 만들지 않는 것이 싸다. 행 단위 과금이 없어 재고 5만 행을 정규화 테이블로 둘 수 있다. 대가로 개인정보가 외부에 저장되고 백업이 없다 (`PRODUCT.md` · S4) |
| 런타임 | **Node + Next.js** | D1을 안 쓰면 Workers를 쓸 이유가 없다. Workers 무료는 요청당 CPU 10ms로 동기화가 불가능해 비용 이점도 없다 (S1) |
| 자동 동기화 등록 | **Phase 8(알림)에서 건다.** Phase 2는 `[수집]` 버튼과 `/api/sync`까지만 (2026-08-20 결정) | 스케줄이 실제로 필요해지는 것은 알림이다. 개발 기간에는 수동 수집으로 충분하고, Supabase 일시정지 방지만을 위해 스케줄을 걸 이유는 없다. 등록 파일(`scripts/`)은 만들어 두고 걸지 않는다 |
