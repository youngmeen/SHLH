# 기술 스펙

제품 문서(`PRODUCT`·`REQUIREMENTS`·`DOMAIN`)가 **무엇을 만들 것인가**를 정한다면, 이 문서는 **어떻게 만들 것인가**를 정한다.

규칙 세 가지.

1. 결정한 것은 근거와 함께 적는다. 근거 없이 이어받은 결정은 결정이 아니라 관성이다.
2. 아직 정하지 않은 것은 `결정 필요`로 남긴다. 정한 척하지 않는다.
3. 사실은 확인한 것만 적는다. 확인 방법과 날짜를 함께 남기고, 확인하지 못한 것은 6절에 모은다.

## 1. 확정된 스펙

### 1.1 실행 형태

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 사용 인원 | 1인 개인 도구 | 로그인·권한·멀티테넌시를 만들지 않는다 |
| 실행 위치 | 로컬 맥 | 무료로 하루 2회 동기화를 돌릴 수 있는 유일한 구성이다(아래 비용 비교) |
| 런타임 | **Node + Next.js** | Supabase·PDF 파싱과 마찰이 없다. vinext·Workers·D1은 제거한다 (S1) |
| 저장소 | **Supabase Postgres (Free)** | 배포 시 저장소를 다시 만들지 않는다. 행 단위 과금이 없다 |
| 알림 | 텔레그램 발송 전용 | 나가는 요청만 있으므로 공개 URL이 필요 없다 |

배포 시 비용 (2026-08-20 확인)

| 구성 | 월 비용 | 하루 2회 동기화 |
| --- | --- | --- |
| **로컬 실행 + Supabase Free** | **$0** | 가능 |
| Workers Paid + Supabase Free | $5 | 가능 |
| Workers Free | $0 | **불가** — 요청당 CPU 10ms. 재고 자치구 하나가 3.9MB JSON이다 |
| Vercel Hobby | $0 | **불가** — Cron 하루 1회 |
| Render Free | $0 | **불가** — 15분 후 sleep |

Supabase Free 한도: DB 500MB · Egress 5GB/월 · Storage 1GB · 프로젝트 2개 · **API 요청 무제한(행 과금 없음)** · **백업 없음** · **1주 비활성 시 일시정지**. 재고 5만 행은 약 30~50MB로 한도의 10% 이하다.

### 1.2 수집

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 마이홈(LH) | 공공데이터포털 Open API | 공식 데이터. 인증키(`DATA_GO_KR_API_KEY`)는 서버에서만 읽는다. **계정 인증키 하나로 활용신청이 승인된 모든 API를 호출한다** — API를 늘려도 키는 그대로다 |
| SH | 공식 게시판 HTML 파싱 | API가 없다 |
| 상세 | 공식 상세 페이지 HTML | 목록에 없는 자격·임대조건이 상세에만 있다 |
| 요청 실패 | 소스별로 독립 처리 | 한쪽이 죽어도 다른 쪽 공고는 보여준다. 전부 실패하면 502 |
| 재시도·타임아웃 | 마이홈 1회 재시도, 요청 타임아웃 12초 | 현재 코드 값. 유지한다 |

### 1.3 출처의 계층

출처를 한 종류로 취급하지 않는다. 안정성과 비용이 다르므로 층을 나누고, **싼 층부터 쓰되 위 층이 아래 층을 대체하지는 않는다.**

| 층 | 예 | 안정성 | 쓰는 방식 |
| --- | --- | --- | --- |
| A. 문서화된 공개 API | 마이홈(data.go.kr) | 규약이 있고 필드가 문서화됨 | 기본 수집 경로 |
| B. 공식 사이트의 내부 JSON | 서울주거포털 `maplist.json` | 공식 데이터지만 **비문서화. 예고 없이 바뀐다** | 쓴다. 단 파서를 격리하고, 깨지면 `unknown`으로 떨어뜨린다(R43). 회귀 테스트로 응답 형태를 고정한다 |
| C. 공식 게시판 HTML | SH 게시판 | 마크업이 바뀌면 깨진다 | **공고 발견의 유일한 경로.** 실측: 마이홈 API 서울 5건 vs SH 게시판 30건 |
| D. 첨부파일 · 수동 입력 | 공고문 PDF·HWPX | 획득 자체가 막혀 있다(S1) | 최후 수단. A~C로 얻지 못하는 값에만 |

A~C가 서로를 대체하지 않는다는 점이 중요하다. 공고 발견은 C가, 주택 단위 정보는 A가, 좌표·대중교통은 B가 준다. **하나만 보면 누락이 생긴다(R1).**

### 1.4 데이터 신뢰성 구현 규칙

`REQUIREMENTS` 15절을 코드에서 지키는 방식이다.

- 모든 값은 출처를 함께 저장한다: `official` / `calculated` / `inferred` / `unknown`
- 조회 실패, 정보 없음, 미발표를 서로 다른 상태로 저장하고 화면에서도 다르게 표시한다
- 공식 자료에 없는 값은 `null`로 두고 채우지 않는다
- 추론값(관심도·우선순위)은 계산값과 구분해 저장한다

### 1.5 보안 구현

- 인증키는 서버 코드에서만 읽는다. 응답·HTML·오류 메시지·로그에 넣지 않는다
- 외부 페이지를 읽는 요청은 허용 목록만 통과시킨다: `https` + `apply.lh.or.kr` / `i-sh.co.kr` / `www.i-sh.co.kr`
- 허용 검사는 **상세 조회뿐 아니라 수집 단계에도** 적용한다 (현재 미적용, G1)
- 프로필은 로컬 저장소에만 두고 외부로 전송하지 않는다
- 인증수단을 보관하지 않고 청약을 자동 제출하지 않는다

### 1.6 테스트

- 실제 응답을 픽스처로 고정한 회귀 테스트를 쓴다. 네트워크에 의존하는 테스트를 만들지 않는다
- 수집·판정·상세 추출·서버 렌더링·스키마 일치를 덮는다
- 스키마는 수동 생성문과 drizzle 산출물이 어긋나면 실패하게 둔다
- 실행: `npm test` (`node --test tests/*.test.mjs`). 확인: 2026-08-20 기준 **80개** 전부 통과
- 파싱 규칙을 고칠 때는 그 케이스를 고정하는 테스트를 함께 추가한다

### S1. 런타임 — **Node로 이동 (2026-08-20 결정)**

기존 구성은 Next.js App Router 문법 + vinext(Vite) + Cloudflare Workers + 로컬 D1이었다. vinext-starter 템플릿에서 시작해 생긴 조합이고 제품이 요구한 것이 아니다.

**Supabase로 저장소를 옮기기로 하면서 Workers를 쓸 이유가 사라졌다.**

1. 로컬 D1이 Workers를 쓰는 유일한 실익이었다
2. Postgres는 TCP 연결이라 Workers에서는 `supabase-js`(HTTP)로만 되고 Drizzle 쿼리를 쓸 수 없다
3. Phase 3의 PDF 파싱도 Node가 필요하다
4. **배포해도 Workers 무료로는 동기화가 불가능하다**(요청당 CPU 10ms). 비용 이점이 없다
5. 저장 코드를 쓰기 전이 가장 싼 이동 시점이다

이동 범위

```text
제거: vinext · wrangler · @cloudflare/vite-plugin · vite · worker/index.ts · db/env.ts · .openai/hosting.json
추가: Drizzle(postgres) + Supabase 접속
수정: package.json 스크립트(next dev/build/start) · db/index.ts · tests/rendered-html.test.mjs
부수 이득: vinext 0.0.50(1.0 이전) 의존이 사라진다
```

환경변수는 두 개로 정리한다 — `DATA_GO_KR_API_KEY`, `DATABASE_URL`(Supabase Postgres). Supabase Data API는 사용하지 않으므로 anon key는 두지 않는다.

### S2. 저장 스키마 — **결정됨 (2026-08-20)**

저장소는 Supabase Postgres다(S1). D1의 제약(바인딩 100개·요청당 쿼리 수·행 단위 과금)이 없어졌으므로 **정규화 테이블로 그대로 설계한다.** 앞서 검토했던 자치구별 JSON 캐시 방식은 D1 과금을 피하려던 우회였으므로 쓰지 않는다.

기존 `profile`(JSON 1행)·`sent_notice`·`applied`는 Postgres로 옮기고, 아래 네 테이블을 추가한다.

| 테이블 | 단위 | 담는 것 |
| --- | --- | --- |
| `notice` | 공고 1건 | 출처·식별자·공고명·기관·유형·접수기간·발표일·상태·원문 URL·**최초 확인 시각**·갱신 시각·원문 스냅샷 |
| `housing_unit` | 주택 1호(또는 주택형) | 공고 또는 재고에서 온 주택. 단지명·주소·PNU·호수·전용면적·세대수·보증금·월임대료·**값의 출처**(1.4)·마지막 갱신 시각 |
| `follow_up_notice` | 후속공고 1건 | 결과·당첨자·정정 공고. 원 공고 참조(`beforePblancId` 또는 제목 매칭)·원문 URL·스냅샷 |
| `sync_run` | 동기화 1회 | 실행 시각·소스별 성공/실패·수집 건수·오류 메시지 |

원칙

- **원문 스냅샷을 보관한다.** 파싱 규칙을 고쳤을 때 과거 결과를 다시 만들 수 있어야 한다.
- 값의 출처는 `housing_unit`의 칼럼으로 둔다(`official`/`calculated`/`inferred`/`unknown` + 어느 API·문서에서 왔는지).
- 재고(단지정보 API)에서 온 주택과 공고에서 온 주택을 같은 테이블에 두되 출처로 구분한다. 둘을 잇지 못하면 잇지 않은 채로 둔다(5절의 이름 불일치).
- 공급유형·순위(SupplyCategory)는 Phase 3에서 자격을 붙일 때 테이블로 만든다. Phase 2에서는 추출되면 `notice`에 문자열로 남긴다.
- Postgres 기능을 쓴다 — 원문 스냅샷과 API 원본은 `jsonb`, 자치구·유형·면적·보증금·월임대료에 인덱스, 재고는 자치구 단위로 교체(`delete` + 다중행 `insert`).
- **원문 스냅샷은 자치구·공고별 최신 1개만 보관한다.** 자치구 응답이 3.9MB인데 누적하면 무료 티어 500MB를 며칠에 소진한다.

`sync_run`이 없으면 "공고가 없음"과 "수집 실패"를 구분할 수 없다(R43). 화면은 이 이력을 읽어 마지막 성공 시각과 실패한 소스를 표시한다.

### S3. 첨부파일 — **Phase 2에서 제외, Phase 3 과제**

소스별로 어디까지 API로 되는지는 5절에서 확정됐다.

| 소스 | 공고 발견 | 주택 정보 | 전용면적 | 좌표·대중교통 |
| --- | --- | --- | --- | --- |
| LH(마이홈) | 모집공고 API | 모집공고 API (주택 단위) | 단지정보 API | 주소·PNU (지오코딩 필요) |
| SH 매입임대·공공임대 | SH 게시판 + 서울주거포털 | 단지정보 API (호 단위) | 단지정보 API | 주소·PNU |
| 청년안심주택 | SH 게시판 + 서울주거포털 | 서울주거포털 JSON | 부분 (`roomTotArea`) | 좌표·지하철 도보시간 |

**Phase 2에 필요한 값은 전부 API로 얻는다.** 첨부파일은 다루지 않는다.

첨부에만 남는 것은 둘이고 모두 Phase 3 이후다.

1. **자격 조건**(소득·자산·순위) — 어떤 API에도 없다. LH 첨부 PDF는 인증 없이 열리고 텍스트도 추출된다
2. **공고별 모집 호실** — 재고는 알지만 공고의 브랜드명과 재고의 건물명이 어긋난다

SH 첨부는 Innorix 때문에 서버가 직접 받을 수 없다. 필요해지면 헤드리스 브라우저와 사용자가 파일을 넣는 수동 경로 중에서 고른다. Innorix 역구현은 권하지 않는다.

얻지 못한 값은 `unknown`으로 두고 원문 링크를 제공한다.

### S4. 누적 데이터 백업 — **Phase 2에 포함 (필수)**

제품 가치의 절반이 누적 기록(지원 이력·경쟁률·판정 근거)에 있다. **Supabase 무료 티어는 백업을 제공하지 않고, 1주 방치하면 프로젝트가 일시정지된다.** 그래서 선택이 아니라 필수다.

- 내보내기(JSON) 엔드포인트를 만든다. 프로필·지원 이력·공고·주택을 한 파일로 내려받는다
- 동기화가 성공할 때마다 최신 내보내기를 로컬에 한 부 남긴다(동기화가 하루 2회 돌므로 일시정지도 함께 예방된다)
- 재고(단지정보 API 결과)는 다시 받으면 되므로 백업 대상이 아니다

### S5. 위치·경로 API — **Phase 4**

- 주소 → 좌표 지오코딩 수단
- 대중교통 Door-to-Door 경로 API, 호출 한도와 캐시 정책
- 주소를 얻지 못한 주택을 자치구 대표 좌표로 근사할지, `확인 필요`로 둘지 (근사값은 `inferred`)
- 외부 API에 보내는 값의 범위 (R47)

### S6. 동기화와 알림 실행 경로 — **동기화 결정됨 (2026-08-20)**

동기화는 Phase 2, 발송은 Phase 8이다. 저장이 먼저 있어야 알림이 보낼 내용을 갖는다.

```text
app/lib/sync.ts          ← 로직 (수집 → 저장 → 결과 요약). 한 곳에만 둔다
app/api/sync/route.ts    ← 화면의 [수집] 버튼과 launchd가 같이 호출
app/lib/notify.ts        ← Phase 8. 저장된 결과를 읽어 발송
```

**주기: 하루 2회, 09:00과 18:00.** 하루 1회면 최악 약 24시간 지연이라 Phase 8 완료 조건(12시간 이내)을 만족하지 못한다. 2회면 최대 15시간이다.

**대상별 주기를 나눈다.** 실측 근거는 5절이다.

| 대상 | 크기 | 주기 |
| --- | --- | --- |
| 공고 (모집공고 API · SH 게시판 · 서울주거포털) | 수백 KB | 하루 2회 |
| 재고 (단지정보 API, 자치구 단위 1회 호출) | 자치구당 0.1~4MB, 1~4초 | 캐시 만료(7~30일) 또는 공고에 새 자치구가 등장할 때 |

호출량은 공고 2회 + 재고 0~2회로 하루 5회 미만이다. 개발계정 한도 1,000회/일의 1%에 못 미친다.

**알려진 한계** — 맥이 절전이면 그 시각에 실행되지 않는다. launchd는 깨어난 직후 밀린 작업을 한 번 실행한다. 보완책으로 SH 공식 청약알리미(카카오톡)를 병행한다.

Phase 8에서 정할 것 — 발송 채널 설정, 재알림 정책(R32), 마감 임박 알림.

### S7. 지원 결과 수집 — **Phase 9**

### 마이홈 모집공고 API — `1613000/HWSPR02/rsdtRcritNtcList`

### 서울주거포털

- SH 공공임대 목록(`housing.seoul.go.kr/site/main/sh/publicLease/list`)이 HTML 표로 청약유형·공고명·공고일·**발표일·모집상태**·담당부서를 준다. 한 페이지 10행, `cp=N`으로 넘긴다
- 상세(`…/view?seq=N`)에 **접수기간(시각까지)·당첨자발표일·총 공급호수**가 있다. 지금 SH 게시판 파싱은 이 값이 전부 `null`이다. 다만 주택별 주소·면적·임대료는 없다
- **조인 키를 찾았다 (2026-08-20).** 목록의 "바로가기" 링크(`i-sh.co.kr/…/m_241/view.do?seq=NNNNNN`)가 SH 게시판 게시물 seq를 그대로 담는다. 게시판이 준 seq(308799·308644·308571·308569)와 정확히 같았다. 제목 매칭 같은 추측이 필요 없다. 2페이지(20행)에서 게시판 공고 30건 중 **14건**이 붙었다
- **주의** — 포털 상세 URL의 `seq`는 게시물 ID가 아니라 목록에서의 행 번호다(1행이 seq=1). 새 공고가 올라오면 전부 밀리므로 저장해서 재사용할 수 없다. 목록을 읽은 그 자리에서만 따라간다
- 열 순서를 고정하면 안 된다 — `모집상태` 열이 조건부로 렌더된다. `thead`를 읽어 열을 찾는다
- 본문 표기가 공고마다 다르다. 실측한 네 가지: `■ 접수기간 : 2026.08.19.(수) ~ 2026.09.17.(목) 18시` / `■ 접수일` 다음 줄에 `○ 인터넷접수: 2026.08.31. ~ 2026.09.02.` / **마감일에 연도가 없는** `2026.08.18.(화) ~ 08.28.(금) 18:00` / **순위·접수방법별로 `-` 세부 줄에 나뉜** 형태(인터넷 1순위 8.18~8.19, 2순위 8.20 당일, 우편 8.13~8.14). 마지막 형태는 항목 줄만 보면 접수기간이 통째로 빈다. 여러 구간은 가장 이른 시작 ~ 가장 늦은 마감으로 모은다
- `서류제출기간`·`서류심사대상자 발표`는 접수가 아니다. 대괄호 안의 `소인분`·`도착분` 날짜도 접수기간이 아니다
- 본문 앞머리 안내문이 항목과 같은 낱말을 쓴다 — "당첨자 발표 전 공개하지 않으니"가 발표일 줄보다 먼저 나온다. `■`·`○`로 시작하는 항목 줄만 봐야 한다
- 공급호수는 문장으로 온다 — `G밸리하우스-5세대, 소셜믹스형 청년주택-7세대 (총12세대)`. 숫자로 눌러 담으면 어느 단지 몇 호인지 잃는다
- SH 공식 공급유형 분류: 장기전세주택 · 장기안심주택 · 국민공공임대주택 · 매입임대주택 · 재개발임대주택 · 도시형생활주택 · 수요자맞춤형 · 청년안심주택 · 행복주택 · 희망하우징 · 두레주택 · 전세임대
- 유형 표기가 출처마다 다르다 — 같은 공고를 SH 게시판은 `신혼신생아매입임대주택Ⅱ`, 포털은 `도시형생활주택`으로 부른다(실제 계열은 장기전세2 미리내집)
- 청년안심주택 단지 JSON(`soco.seoul.go.kr/youth/pgm/home/yohome/maplist.json`)은 **인증키 없이** 단지 50개를 준다 — **좌표(`xpos`·`ypos`)와 지하철 도보시간(`optionSubway`)** 포함(49/50)

### LH 청약플러스와 공고문 PDF

- **LH 첨부는 인증 없이 받아진다.** `apply.lh.or.kr/lhapply/lhFile.do?fileid=…` GET → 587KB PDF
- PDF에 텍스트 레이어가 있어 `pdftotext -layout`로 126KB 텍스트가 나오고 **주택형 표가 그대로 보인다**(단지명·주택형·세대수·전용면적·보증금·월임대료). 셀 병합 때문에 파싱은 단순하지 않다
- 공고문에 **"입주자모집공고일이 입주자격 판단기준일"**이 명시되고 청년 나이가 출생일 범위로 표기된다. R12와 일치한다
- 마이홈 포털 상세(`pcUrl`)에는 쓸 것이 없다(표 3개, 전용면적·임대료 0회)

### 공고 ↔ 재고 매칭의 한계

- **조인 규칙을 실제 데이터로 검증했다 (2026-08-20).** 마이홈 모집공고가 준 `서울번동3`(강북구 오현로 208)을 강북구 재고 2,536행에 붙였더니 `서울번동3 고령자복지주택(행복주택)` 4행이 걸렸고 전용면적은 **16.99 · 21.99 · 26.99 · 44.68**이었다. 공고문 PDF에서 읽은 21.99·44.68이 그 안에 있다. 같은 규칙으로 `소셜믹스형 청년주택`과 `특화형`은 **0행(미확보)**이다
- 규칙은 **한 방향**이다 — 재고의 건물명이 공고의 단지명을 품을 때만 잇는다. 반대를 허용하면 `소셜믹스형 청년주택`이 `청년주택`이라는 이름의 아무 단지에 붙는다
- 단지명에서 공식 공급유형 낱말만 떼어낸다. `청년주택`·`특화형` 같은 사업 브랜드명을 유형으로 보면 남는 낱말이 짧아져 엉뚱한 단지에 붙는다
- 금천구 공고의 `G밸리하우스`는 재고 API에 48행 있다(성공). 그러나 같은 공고의 `소셜믹스형 청년주택`, 성북구 공고의 `특화형`·운영기관명은 **0행**이다
- **공고는 사업 브랜드명, 재고 API는 물리적 건물명을 쓴다**
- 단지명 품질이 고르지 않다 — `유어스빌리지(시흥동 108-3)`·`독산로22길93-7`·`가동`·`-`·`서울특별시 금천구`가 섞여 있다(금천구 4,825행의 고유 이름 169개)

### 저장 경로 실행 결과 (2026-08-20)

`DATABASE_URL`을 넣고 실제로 돌려서 확인했다.

- **접속은 Connection Pooler로만 된다.** 직접 연결 호스트(`db.<ref>.supabase.co`)는 **AAAA 레코드만** 있어 IPv6 경로가 없는 맥에서는 `ENOTFOUND`다. 이 프로젝트의 pooler는 `aws-1-ap-northeast-2.pooler.supabase.com:5432`, 사용자는 `postgres.<ref>` 형식이다(`aws-0-*`는 테넌트를 모른다고 답한다). PostgreSQL 17.6
- `npm run db:migrate`로 7개 테이블 생성 — `notice`·`housing_unit`·`follow_up_notice`·`sync_run`·`profile`·`sent_notice`·`applied`
- `[수집]` 1회: 공고 35건(마이홈 5 + SH 30) · 주택 1건 · 후속공고 20건 · 재고 자치구 5개, **14~18초**
- 같은 공고를 다시 저장해도 `first_seen_at`은 유지되고 `updated_at`만 바뀐다(확인)
- 재고는 4회 실행에 걸쳐 자치구 20개·**약 3.6만 행**이 들어갔다(자치구당 상한 5개씩)
- SH 공고 30건 중 **`모집중` 7건은 접수기간이 전부 채워졌다.** 못 채운 3건은 모집마감 2건과 정정공고 1건이다
- 내보내기 101KB(재고 제외), 로컬 백업 `backups/jib-alim-export.json` 생성 확인. 프로필 저장·조회 왕복 확인
- 조인 실행 결과: `서울번동3`(마이홈) → 재고 4행, 전용 **16.99·21.99·26.99·44.68**, 유형까지 일치
