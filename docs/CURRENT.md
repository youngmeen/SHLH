# 집알림 CURRENT — Phase 2 구현 계획

이 문서가 Phase 2의 구현 계획이다(`ROADMAP.md` 6절이 요구하는 항목을 담는다). Phase 2가 끝나면 Phase 3 내용으로 교체한다.

## 1. 현재 단계

**Phase 2. 공급주택 구조화와 저장**

공고 안에 실제로 어떤 주택이 공급되는지 구조화하고, 수집 결과를 저장한다. 추천·알림 발송·자격 판정·출퇴근 계산은 하지 않는다.

## 2. 현재 상태

Phase 0(서울 공고 수집)과 Phase 1(로컬 D1·프로필 저장)이 끝났다. 완료 범위와 빠진 항목은 `ROADMAP.md` 2절에 있다.

이번 단계에서 알고 있어야 할 것

- 수집한 공고를 **저장하지 않는다.** 요청할 때마다 수집하고 버린다
- 마이홈 API가 주는 **주택 단위 행을 버리고 있다**(`SPEC.md` G10)
- SH 공고의 접수기간·발표일이 `null`이다. 서울주거포털에 있는데 쓰지 않는다
- 후속공고를 폐기한다(G3). 정정공고를 구분하지 않는다(G4·G11)
- 프로필이 나이를 숫자로 저장한다(G8). **Phase 3 착수 전에 생년월일로 전환한다**

## 3. 스파이크로 확정된 전제 (2026-08-20)

착수 전에 출처를 실제로 호출해 확인했다. 상세는 `SPEC.md` 5절이다.

| 필요한 것 | 어디서 오는가 |
| --- | --- |
| 공고 발견 | 마이홈 모집공고 API(서울 5건) + SH 게시판(30건). **API만 보면 SH를 놓친다** |
| 접수기간·발표일·모집상태 | LH는 모집공고 API에 전부 있음. **SH는 서울주거포털** |
| 주택 단위 정보 | 마이홈 모집공고 API(주택 단위 행) + **마이홈 단지정보 API**(호 단위, 주소·PNU·보증금·월임대료) |
| 전용면적 | **단지정보 API** (`suplyPrvuseAr`). 표본 500행 전부 채워짐 |
| SH 매입임대 | 단지정보 API에 `insttNm=SH공사`로 들어 있다. 서울 25개 구 합계 52,738행 |
| 정정공고 판별 | 모집공고 API의 `sttusNm`·`beforePblancId` |

**첨부파일 PDF는 이번 단계에서 다루지 않는다**(`SPEC.md` S3).

**런타임과 저장소를 옮긴다** — Supabase Postgres를 쓰기로 하면서 Cloudflare Workers를 유지할 이유가 사라졌다(`SPEC.md` S1). 저장 코드를 쓰기 전인 지금이 가장 싼 시점이다.

확인된 한계 — 공고에 적힌 사업 브랜드명(`소셜믹스형 청년주택`, `특화형`)이 재고 API의 건물명과 어긋난다. 이름이 맞는 경우(`G밸리하우스` 48행)만 정확히 잇고, 나머지는 자치구+유형 수준으로 느슨하게 두거나 `미확보`로 표시한다.

## 4. 이번 단계 목표

```text
[수집] 버튼 또는 09:00·18:00 동기화
        ↓
공고 3소스 수집 → 저장 (최초 확인 시각 기록)
        ↓
공고의 자치구 재고를 단지정보 API에서 확보 (캐시)
        ↓
공고를 열면 그 안의 주택 목록과 조건에 맞는 재고를 함께 본다
```

## 6. 저장 스키마

`SPEC.md` S2에 확정했다. `notice` · `housing_unit` · `follow_up_notice` · `sync_run` 네 테이블.

- Postgres이므로 정규화 테이블로 그대로 둔다. 원문은 `jsonb`, 자치구·유형·면적·보증금·월임대료에 인덱스
- 값마다 출처를 남긴다(`official`/`calculated`/`inferred`/`unknown` + 어느 API인지)
- 원문 스냅샷은 **자치구·공고별 최신 1개만** 보관한다. 무료 티어 500MB를 지켜야 한다
- 재고는 자치구 단위로 교체(`delete` + 다중행 `insert`)한다. 호수 키가 일정하지 않다
- `sync_run`이 없으면 "공고 없음"과 "수집 실패"를 구분할 수 없다(R43)

## 7. 동기화

`SPEC.md` S6에 확정했다.

- 공고: 하루 2회(09:00·18:00). 하루 1회면 Phase 8 완료 조건(12시간 이내)을 못 맞춘다
- 재고: 캐시 만료(7~30일) 또는 공고에 새 자치구가 등장할 때. 자치구당 1회 호출·1~4초·0.1~4MB
- 수동 `[수집]` 버튼과 스케줄이 같은 함수를 호출한다
- 맥이 절전이면 실행되지 않는다. SH 공식 청약알리미를 안전망으로 병행한다

## 8. 백업 (S4 · 필수)

Supabase 무료 티어는 **백업이 없고 1주 방치 시 일시정지**된다.

- 프로필·지원 이력·공고·주택을 한 파일로 내려받는 내보내기(JSON)를 만든다
- 동기화가 성공하면 최신 내보내기를 로컬에 한 부 남긴다
- 재고는 다시 받으면 되므로 백업 대상이 아니다

## 9. 하지 않는 것

- 텔레그램 발송 (Phase 8 — 저장까지만 한다)
- 자격 판정 고도화, 프로필 생년월일 전환 (Phase 3)
- 출퇴근 계산, 경기도 수집 확장 (Phase 4)
- 전세임대 전용 분석 (Phase 5)
- 과거 경쟁률 계산 (Phase 6 — 후속공고는 보관만)
- 추천 순위 (Phase 7)
- 첨부파일 PDF 파싱 (`SPEC.md` S3)
- Supabase 배포·호스팅 구성 (로컬 실행 유지. 배포는 필요해질 때 결정)
- 지도·지하철·조감도, 최종 청약 자동화

발견한 것은 구현하지 않고 `SPEC.md` 3절에 적는다.

## 10. 검증 방법

실제 응답을 픽스처로 고정한 회귀 테스트를 쓴다. 네트워크에 의존하는 테스트를 만들지 않는다.

고정할 케이스

1. 마이홈 모집공고 응답에서 **한 공고의 여러 주택 행이 각각 살아남는다** (구리·남양주 행복주택 4행)
2. 단지정보 API 응답이 **호 단위로 파싱된다** (`styleNm` 201·202, 전용면적·보증금·월임대료)
3. 조인 성공 케이스 — `서울번동3` ⊂ `서울번동3 고령자복지주택(행복주택)`, 유형까지 함께 매칭
4. 조인 실패 케이스 — `소셜믹스형 청년주택`은 재고에 없다. **`미확보`로 남고 임의 매칭하지 않는다**
5. 후속공고가 모집공고 목록에서 제외되되 **저장된다**
6. 정정공고(`sttusNm=정정공고`)가 원 공고(`beforePblancId`)에 연결된다
7. 서울주거포털에서 SH 공고의 접수기간·발표일·모집상태가 채워진다
8. 소스 하나가 실패해도 나머지가 저장되고 `sync_run`에 실패가 남는다

샘플 공고는 유형별로 최소 5건(LH 행복주택·LH 전세임대·SH 매입임대·SH 수요자맞춤형·청년안심주택)을 사람이 확인한 결과와 대조한다.

## 11. 완료 조건

### 데이터

- 공고를 저장하고 **최초 확인 시각**이 기록된다
- 한 공고에서 0개 이상의 주택을 만들고, 마이홈 주택 단위 행이 버려지지 않는다
- 재고를 자치구 단위로 저장하고 전용면적·주소·PNU·보증금·월임대료를 갖는다
- 후속공고가 폐기되지 않고 보관된다
- 정정공고가 구분되고 원 공고에 연결된다
- SH 공고의 접수기간·발표일·모집상태가 채워진다
- 공식 자료에 없는 값을 만들지 않는다. 잇지 못한 것은 `미확보`로 남는다
- 값의 출처를 확인할 수 있다

### 동작

- 프로필·지원 이력이 Supabase에 저장되고 재시작 후에도 유지된다
- 내보내기로 내 데이터를 한 파일로 받을 수 있다
- `[수집]` 버튼과 `/api/sync` 호출이 같은 결과를 낸다
- launchd가 09:00·18:00에 호출하고 결과가 `sync_run`에 남는다
- 소스 하나가 실패해도 나머지가 저장되고, 화면이 마지막 성공 시각과 실패한 소스를 보여준다
- 공고를 열면 그 자치구 재고에서 조건에 맞는 주택을 확인할 수 있다

### 검증

10절의 8개 케이스가 회귀 테스트로 고정되고 `npm test`가 통과한다.

## 12. Phase 완료 후

**Phase 3. 지원 자격 판정**으로 이동한다. 착수 전에 두 가지를 정한다.

1. 프로필을 생년월일 기반으로 전환한다(G8)
2. 자격 조건은 공고문 PDF에만 있으므로 PDF 파싱과 런타임 이동을 함께 판단한다(`SPEC.md` S1·S3)

## 13. 작업 규칙

구현 범위는 상위 문서보다 이 문서를 우선한다. 상위 문서와 충돌하는 구현은 하지 않는다.

현재 단계와 관계없는 기능은 함께 구현하지 않고 `SPEC.md` 3절에 적는다.

기존 코드가 이미 제공하는 기능을 확인한 후 수정하며 같은 기능을 새로 만들지 않는다(5절).

문서 읽는 순서와 나머지 규칙은 `CLAUDE.md`에 있다.
